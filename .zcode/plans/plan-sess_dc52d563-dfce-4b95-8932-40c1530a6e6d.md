# mini 档「时间∧步骤」升档判据修订（task-tier-gate-20261124）

## Context：缺陷确认（分析结论）

**现状机制**（已亲读验证）：init 缺省 mini（init-session.sh:639-664 → mini-lite 单 Phase 模板）→ posttooluse hook `tier_upgrade_check`（zcode-posttooluse.sh:226-281）**纯时长触发**：`now-created_at > TASK_PLANNER_TIER_UPGRADE_MINUTES(默认15)` 即一次性执行 `set plan_tier=standard + TU-1 decision + render + 删 stale attest 锁`，检查面随之恢复标准档（委派门 floor 0.7、VC 5/2、审计门 L1、goal-gate、六文档回读）。升档不换模板文件，render 全语义重建（planctl.py:1979-2019），`plan_tier≠mini` 分支补回调研区块（:1567）与 template_body 附录（:1781）。

**缺陷成立（实证）**：判据只看墙钟时长、不看任何进度。本仓近期 13 个有效样本时长 52/54/64/71/75/111/118/235/274/353/610min——**全部 >15min**（perf-default-mini 本任务自己就 75min）；调研子代理单段即耗数分钟，15min 阈值下几乎所有任务都在调研阶段中或刚出调研时被升档 → mini 缺省档退化为「所有任务的前 15 分钟临时态」，与用户「至少完成调研后升档才有参考价值」裁决冲突。

**判据信号可用性**（已验证 plan-state.json 权威字段）：`phases[].status ∈ pending/in_progress/complete`（planctl.py:486,1312）、`findings[]`（:97）、`delegations[]`（:52）均可 jq 直查；S-unit 状态无 JSON 跟踪（render 恒写 pending，:1612），不可用作信号。

## 修订方案：双判据 = 时长阈值 ∧ 步骤进度门 + 硬阈值兜底

`tier_upgrade_check` 在时长达标后增加**步骤进度门**（全客观信号，无主观判断）：

```
升档 ⇔ elapsed>threshold(15min) ∧ 步骤门满足
     ∨ elapsed>硬阈值(45min)          ← 兜底：调研卡死/无簿记任务不被永久困在 mini
步骤门（三选一）:
  ① 任一 phases[].status=="complete"   （多 Phase 计划：Phase 1 调研完成）
  ② findings 数组非空                  （调研结论已落盘）
  ③ delegations 数组非空               （派发已簿记登记）
```

- 新 env：`TASK_PLANNER_TIER_UPGRADE_HARD_MINUTES`（默认 45，非数字/0 回落 45，同 threshold 兜底范式）
- 未满足门时 return 0 静默等待下轮 hook 复查（幂等 state 文件仍只在真升档时写）
- TU-1 decision 文本与 `[tier-upgrade]` emit 文案注明触发原因（步骤门哪种信号 / 硬阈值兜底）
- 依据=用户 2026-11-24 原话：「结合时间以及 todo步骤进行升级…至少完成调研后才做决定，调研后做升级才具有参考价值」——实施开工时先经 planctl 登记进活跃计划 Decisions + user-session-log（即时落盘纪律）
