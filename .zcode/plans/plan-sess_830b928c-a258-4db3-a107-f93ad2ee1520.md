# 任务：验证技能独立化 + 验证脚本强化

## 🎯 用户需求原文（复述）
1. 加强当前技能的验证脚本这部分，验证技能的强化，确保任务执行完成的可验证性
2. 将所有的验证做成**独立技能**，独立于主技能之外，但在主技能相应执行步骤中引用
3. 创建任务的时候都需要写验证的规则以及脚本（可验证性前置）
4. 确保所有任务都经过严格的验证，所有产出以及执行都有验证，确保执行的稳定

## 现状发现
- 已有 10 卫星（Rule 82 分层），**无独立验证卫星**
- 验证能力分散：VC 规则（`goal-gate.md`）+ 子代理验证（`completion-gate.md`）+ `verification.md` 模板都在主技能内；验证规则散在核心（Rule 26/51/66.3）+ task-discipline（Rule 33）
- 验证脚本体系：`check-complete.sh`（124KB，21 门）/`check-3file-gate.sh`/`attest-plan.sh` 等，被 hook/init/78 selftest 深度集成
- VC 模板是描述性占位（`[What to check / test command]`），**没有强制可执行性**——这是"创建任务时写验证规则和脚本"的强化点

## 方案（用户未答命名/归属问题，按推荐执行）
**新卫星命名 `verification-gate`**（guard 类风格）；**验证规则/模板/SOP 独立成卫星，机械层脚本留守主技能 scripts/**（Rule 82 "机械层留守"先例，hook/init 零改动，风险最小）

### 交付物清单

### 关键设计决策
- **不迁移** Rule 26/51/66.3 原文（避免与核心/task-discipline 镜像副本，Rule 82 禁镜像）——验证卫星收编"验证机制规则"，核心执行面规则保留指针
- **不迁移** check-complete 等机械脚本（hook/init/selftest 深度集成，迁移风险高）——验证卫星引用其绝对路径
- **VC 可执行性**是"创建任务时写验证规则和脚本"的核心强化：模板强制 + attest 门强制 + run-verification.sh 统一执行
