# 项目深度巡检 + 全技能审核 方案

## Context（为什么做）

用户原话：「开始对整个项目进行深度巡检，分析到底哪里出了问题。尤其你可以使用Scaler Fix进行嗯对所有的技能进行审核，哪里不合理给出建议。」

拆解为两个交付目标：
1. **诊断**：对 `/mnt/data/dev/task-planner-skill` 做系统性巡检，找出真实存在的结构性问题与根因。
2. **审核**：用 `skill-fix` 技能（本机无 "scaler" 工具，唯一匹配项）批量审核技能，对不合理处给出建议。

**探索阶段已确认的关键事实**（4 个 Explore 代理交叉印证）：
- 项目是 task-planner 技能开发仓：21 个顶层技能 + 10 个 review-library 子技能，核心 `skills/task-planner`（208 文件、161 脚本）。
- 357 个 `SKILL.md` 中仅约 **31 个是正式定义**；288 个 `.backup`、32 个 worktree 镜像、5 个 plans 归档均非审核对象。
- `skill-fix` 自带成熟批量审核 SOP（Step0–1.13 + 4 阶段 + G1–G28 门控 + `subagent_skill_auditor.ts` 工具），可直接复用，无需另造轮子。
- **问题信号已现形**：23 个 pending 任务多为 0/0 空壳；in_progress 的 `task-jsonderive-deploy` 出现 `plan-state.json` 342B 空壳 vs `task_plan.md` 48KB 手写的执行层漂移；hook 仍教直接 Edit MD；历史反复出现部署/传播不同步；git 有 master/main 分叉 + 残留 worktree + 大面积未提交改动。
- 全局宪法保护区（`~/.zcode/skills`、`~/.agents/skills`、`AGENTS.md`）未经授权**只报告不改**。

**范围决策**（用户未回答澄清问题，按推荐默认）：审核 `skills/` 下约 31 个正式技能 + 抽样比对全局部署位一致性。批准时若想改为"全局全量"或"只深挖 task-planner"，直接说明即可。

## 执行方案（本次为 Plan 模式，以下均在批准后才执行）

### Phase 0 — 任务登记
当前活跃计划是 `task-restart-baseline-20261122`（弃旧开新机制），与本任务目标无交集 → 按 Rule 意图切换 D 类：挂起旧计划、`init` 新巡检任务目录、显性通告、`[intent-switch]` 登记。全程只读诊断，不触碰旧计划内容。

### Phase 1 — 项目级深度诊断（"哪里出了问题"）
派发只读诊断，产出带证据的问题清单：
1. **git 健康**：只读核查 master/main 分叉、`wt-tplsys-upgrade-20261117` 残留 worktree、`wt/task-v168-machine-parked` 遗留分支、工作区大面积未提交的 plan 文件；判定哪些是正常在途、哪些是遗留垃圾。
2. **计划体系执行层漂移**：核对 `plans/INDEX.md` 24 项待处理（1 in_progress + 23 pending）的空壳率；抽样验证 `plan-state.json` 空壳 vs `task_plan.md` 手写的背离是否普遍；检查 hook/模板是否仍在引导直接 Edit MD。
3. **部署一致性**：对 `skills/` 与 `~/.zcode/skills`、`~/.agents/skills` 同名技能做 diff 抽样，量化漂移面。
4. **真实测试基线**：实跑 `skills/task-planner/scripts/run-selftests.sh --fresh`，记录真实 PASS/FAIL（不采信计划文本里的"96 PASS/8 FAIL"口径）。
→ 产出：`项目诊断报告`（每个问题 = 现象 + 证据 path/行号 + 根因 + 建议 + 严重度 P0/P1/P2）。

### Phase 2 — 全技能审核（skill-fix SOP）
范围锁定 `skills/*/SKILL.md`（21 顶层 + 10 review-library），排除 `.backup`/worktree/plans 副本。按 skill-fix 现成 SOP 分层执行：
1. **机械层**：`frontmatter-linter` agent 批量扫 31 个 SKILL.md（name/description/model/tools 必填、name=文件名、model 格式、tools 一致性）→ `[FM-LINT]` 报告。
2. **调用方式层**：`subagent_skill_auditor.ts <skill_dir>` 批量查 S39/S39a 直调违规（跨 skill 脚本直调、子代理越权调 Skill/MCP/搜索）。
3. **冗余与漂移层**：按 S79 R1–R5 查跨技能镜像/同义重复/双树同名/游离副本（只给建议，**不擅自合并**）。
4. **质量层**：按 skill-fix 维度逐技能评 SOP 严谨性（S78）、验证完备（S82）、泛化（S83）、脚本优先（S85）、模板优先（S86）、描述准确性，逐项对照 G1–G28 门控。
→ 产出：每技能问题卡（evidence: path/size/mtime/sha256 + 行号）+ 不合理之处分级建议；不修正案，只出诊断（阶段 2 用户确认后才可能进入修复，本次不进入）。

### Phase 3 — 汇总交付
- 合并 Phase 1 + Phase 2 → 一份总报告，落盘到新任务目录（诊断报告 + 技能审核矩阵 + 建议清单）。
- 遵守 skill-fix S58 收尾：中文总结「已完成 / 产出 / 遗留 / 下一步」，结论标记 COMPLETE / PARTIAL / BLOCKED。

## 关键约束
- **只诊断、不修复**：不修改任何技能、脚本、配置或保护区文件；所有"建议"仅为文字。
- **保护区红线**：`~/.zcode/skills`、`~/.zcode/agents`、`~/.agents/skills`、`AGENTS.md` 只报告不改。
- **证据驱动**：每个问题必须带可复现证据（文件行号或命令输出），禁止推测包装成结论。
- **不碰未授权范围**：不清理 git 残留、不删空壳任务、不做合并——只列建议，等用户单独授权。

## 验证
- 技能审核覆盖 31 个正式 SKILL.md（清单逐一核对，无遗漏、无副本混入）。
- 每个问题条目带 evidence（path + 行号/size/sha256）。
- 项目诊断中每项"问题"有可复现命令或文件证据支撑。
- selftest 基线为实跑数字，写入报告并标注运行时间与命令。
- 总报告含 COMPLETE/PARTIAL/BLOCKED 结论与下一步建议。
