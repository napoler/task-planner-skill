**建制（为什么有这条）**：用户 2026-11-04 R5 指令（逐字锚 plans/task-crossprojauth-20261104/task_plan.md R5 用户原话行）：「在收到新的指令之后，竟然不做新的计划进化计划更新，或者说同步……每次受到任务之后都可以触发一个整理计划的工作……如果不需要的话，那么就继续。如果说需要的话，就先更新计划任务、维护文档。维护完文档再继续……我要求的期望的就是做多重的同步、以及验证等等，确保整个执行的稳定性……无论用户如何打断，或者说提交新的需求，都需要整理成新的任务/新的计划文档。同样的是，如果说用户比方说明确说明说取消这个任务，或者说取消某一个功能的开发，那么也需要进行同步到文档，然后确保无论后面更新多少步，都会有文档同步。」根因：Rule 8 判定面（A/B/C/D 分类+8.1 新任务边界+8.1.1 目标切换触发）虽已建立，但**执行闭环缺失**——① 判定结果无「先文档同步、再执行」硬门（口头接受+直接开做是常态路径，51.1 有禁令但无流程承载）；② 取消/撤销类指令无分类无文档同步义务（E 类缺口——「取消某功能开发」后计划文档仍标该需求待完成，后续步骤与文档矛盾）；③ 打断接续场景（任务 A 执行一半、新任务 B 到达）无断点检查点+顺序执行义务，A 被无痕迹丢弃；④ 同步结果无留痕义务，「有没有同步文档」不可审计（用户「无论后面更新多少步，都会有文档同步」= 痕迹须累积可查）。

**计划同步与反思门协议（P0）**：
- **102.0 总纲（先反思后执行，定义）**：每次用户指令/新诉求/变更/取消到达 → 先走**反思门**四问（①与当前活跃计划 Goal/范围/交付物有无关联 ②若有=哪类（B/C）③若无：是否打断进行中的任务（D 子场景）④是否取消/撤销（E））→ 按 102.1 分类 → **B/C/D/E 类：先按 102.2 同步文档并落盘，再按文档执行；A 类：照常执行（Decisions Made 登记一行）**。禁止「先执行再补文档」；口头接受不落盘=P0 违规（51.1 同判据）。无活跃计划时新指令天然开新计划（Rule 8.1 N/A 口径），本条 N/A。hook 侧 [plan-note] 逐 prompt 反思提示是本条的机制承载（102.4）。
- **102.1 五类判定（Rule 8 判定面扩展 E 类）**：**A** 无计划影响（闲聊/澄清/复述/追问既有事实）→照常执行；**B** 扩展/追加（与当前 Goal 有关、需更新范围/VC/Phase）→更新当前计划；**C** 矛盾/变更（否定既有计划要素、需求变更）→重规划当前计划（Rule 8/74.2 三判门仍适用，本条不重写判定）；**D** 新任务边界（与当前计划三要素零关联）→开新计划目录，旧计划原样保留；**D 子场景=打断接续**（存在进行中任务 A 时新任务 B 到达）→① A 的断点检查点落盘（progress.md 执行痕迹+已完成 S-unit 清单+subagent-state 检查点，Rule 57/62 载体）② B 入计划（新计划目录或并入判定后的当前计划）③ **顺序执行义务**：A 的在途单元做完到可落盘点后才执行 B，或显式登记顺序（用户裁决 或 B 优先+A 挂起登记 `deferred` 一行）——禁止「A 执行一半、B 直接开做」致 A 无断点丢失；**E** 取消/撤销（用户明示取消任务/取消某功能开发/撤销某需求）→102.1e 处置。判定口径=Rule 8/8.1/8.1.1 既有判定面，102 不重定义判定（36.5 管辖二分），102 补 E 类+执行闭环。
- **102.1e E 类取消/撤销（文档同步义务，P0）**：① 计划文档同步——单项取消=在 task_plan.md 对应 Phase/VC/需求行标 `cancelled`（**不删条目，保留审计痕迹**+一行取消理由）；整体取消=task_plan.md 头部登 `outcome: CANCELLED` + 全部未完成 VC 标 `cancelled(<reason>)`（禁标 skipped/failed——口径=「用户授权不做」，非未执行）；② Decisions Made 必填（指令摘要→E 类判定→受影响文档行→取消理由→时间戳）——取消=不可逆决策（不做），未登记=P0 违规；③ 既有产出/分支/worktree 依用户明示处置：未明示删除=产物保留原样登记一行（Rule 90 双提交口径，取消≠抹 git 历史）；用户明示清理=按宪法 §五 展示后执行。「口头取消不落盘」= E 类版 51.1 口头接受不落盘禁令。
- **102.2 计划优先门（先维护文档，维护完再执行）**：B/C/D/E 类判定后、动执行（写/改/派发）**之前**必须完成文档同步落盘——task_plan.md（Goal/scope/Phase/VC/需求原文锚，append-only 原则见 102.3）+ progress.md（执行痕迹）+ findings.md/需求文档（需求锚）+ 原生 Todo（S5，D 类分支含新计划映射），**全部落盘后才开始执行「按文档」**；同步范围按实际判定类最小化（B=扩展项、C=矛盾重规划项、D=新计划+打断接续检查点、E=cancelled 标记），不过度扩张（Rule 88 射程限定）。落盘后自检（多重同步验证）：grep 自检一行留痕 `本指令→<类>→改动文档: <文件:行>×N→执行入口`（入 Decisions Made 或 progress.md），使「是否同步过文档」机器可查；计划被改（attest 锁定存在）→按既有 attest 流程重锁（attest-plan.sh 既有命令，零新键，重锁前置登记按 51.7 口径）。
- **102.3 多重同步与审计痕迹累积**：文档同步**一条指令一行痕迹，累积制**——旧类痕迹行不得被新指令擦写/删除（Rule 90 双提交+54.3 执行诚实同判据）；「无论后面更新多少步都有文档同步」= 痕迹表（指令→类→文档行）逐条可追溯；交付时 5 要素总结含「计划同步状态」一行（已同步文档清单+未决项）。
- **102.4 机制（L0-T + hook 面=用户显式授权，2026-11-04 R5）**：判定面=LLM 行为（102.0 反思门+102.1 五类+102.2 门+102.1e）+本条款文本锚+UPS hook [plan-note] 逐 prompt 反思提示（zcode-userpromptsubmit.sh：note 文案五类指引+E 类取消关键词检测（取消/撤销/作废/不做了/不要了/放弃/停掉等）+note 与 10 计数限流解耦=每 prompt 触发一次；重注入块 CA-1 mtime+interval 限流不变；fail-open 不变）；**零新增守护脚本/零新 config 键**（hook 编辑=用户 R5 显式「补充一个反思」授权面；`prompt_note_interval` config 键保留不删，改后不再门控 note（避免 config 面变动+AD-11 键数断言级联），键失活状态登记于 hook 头注释；其余机器化 opt-in 未获授权不建）。
