# code-quality-review · 代码质量审查

review-library 兜底池的代码领域审核技能,消费 Rule 42.2 四级检测链第④层。当任务产出为代码/脚本变更（新增函数、重构、CLI 工具、库代码等）,且未命中更细的专用审查需求时,用本技能按代码质量维度做专项审查。
输出二值 `APPROVED` / `CHANGES_REQUESTED`,每条结论必须附机器可复现证据。

## 触发条件
- Rule 42.2 四级检测命中第④层「task-planner 内置 review-library 兜底池」,且任务类型为代码/脚本变更 → 命中本技能。
- 任务产出含 ≥1 个代码文件（.sh/.py/.ts/.js/.rs/.go 等）的修改或新建,且代码量足以承载质量门（非 3 行内 trivial 改动）。
- 交付前做「代码质量门」,或用户/审查者显式要求「代码质量」审查。
- 命中专用审查规则的任务优先专用规则;本技能只处理兜底池内代码面,不替代、不叠加。
- 纯文档、纯配置（非代码语法）、纯调研任务不触发。
- 既有代码重构且 diff 较大（超百行量级）时,即使无新功能,也需过本技能结构/可读性/死代码维度。

## 审查清单
每维度可直接执行（明确检查动作+判定标准）,禁空洞套话:
- [ ] [M] 正确性与边界: Read 每个新增/改动函数,枚举全部分支并逐分支与规格对照;空输入/单元素/超大输入/非法类型至少各构造 1 例心算或实跑
- [ ] [A] 行为一致性判定: 判定边界行为是否与规格一致,归因偏差
  **可选思路**：
  1. 思路 A：规格逐条对照——以任务书规格为基准逐分支核验（适用场景：规格明确、可枚举分支）
  2. 思路 B：边界爆破——构造极端输入观察实际行为再回判规格（适用场景：规格模糊、需反推预期时）
- [ ] [M] 错误处理: grep 裸 `except: pass`、`2>/dev/null` 吞错、缺 else/兜底默认值掩盖异常;确认每处捕获有日志或上报路径,无静默降级
- [ ] [M] 命名与可读性: 抽 3 个新符号,grep 未解释魔数（裸数字/字符串）;统计单函数行数,超 50 行登记待拆分
- [ ] [A] 语义/拆分判定: 判定命名是否与实体语义相符、超标函数是否已合理拆分
  **可选思路**：
  1. 思路 A：陌生人视角——仅凭符号名推断用途，推断不出即不合格（适用场景：公共 API/导出符号）
  2. 思路 B：一致性对照——与邻近既有命名风格逐项对照（适用场景：既有代码库内新增符号）
- [ ] [M] 重复与死代码: grep 新增逻辑块在仓内已有实现（防重复造轮子）;IDE/grep 确认无不可达分支、无 unused import/变量
- [ ] [M] 注释与 docstring: 每新增/改动函数有 docstring（改动类含「原因+时间+原行为」）;无 `TODO` 占位替代修改说明
- [ ] [M] 输入校验: 枚举每个外部入口（CLI 参数/函数参数/API 入参）的校验与失败路径;grep `dict.get(k, default)`、`x or default` 反模式
- [ ] [A] 校验充分性判定: 判定校验是否充分覆盖非法输入、反模式是否真掩盖了错误
  **可选思路**：
  1. 思路 A：非法输入用例——对每个入口构造非法输入看是否被拦（适用场景：入口少、可实跑）
  2. 思路 B：反模式归因——逐处反模式分析是否掩盖配置缺失/falsy 误判（适用场景：入口多、静态分析为主）
- [ ] [M] 并发与资源: 新开的文件/socket/线程/子进程均有成对释放（with/finally/defer）;grep 循环内重复建连接、未设上限的后台任务
- [ ] [M] 依赖与版本: 新增 import/依赖在 lock/manifest 中登记且版本固定（无 `latest` 漂移）;确认无引入与仓内既有依赖冲突的大版本跳变
- [ ] [M] 风格一致性: 抽 2 处改动,与邻近既有代码 diff 缩进/引号/命名/错误返回约定
- [ ] [A] 分叉判定: 判定差异是否属「风格分叉」还是「既有代码本身不规范」
  **可选思路**：
  1. 思路 A：邻近对齐——以邻近代码为基准，新代码向其对齐（适用场景：邻近代码风格统一时）
  2. 思路 B：规范优先——项目有显式 lint/规范时以规范为准（适用场景：邻近代码本身不规范）
- [ ] [M] 测试配套: 核对新功能/修复是否有对应测试或显式登记「无测试+原因」;跑相关测试记录结果
- [ ] [A] 失败归因判定: 判定失败用例归因（本次改动 vs 历史债务）
  **可选思路**：
  1. 思路 A：基线对照——与改动前基线比对差异项（适用场景：有基线记录）
  2. 思路 B：逐例溯源——对失败用例查 git blame/复现路径判定归属（适用场景：基线缺失、失败项多）
- [ ] [M] 越界自检: 变更文件清单与任务书 scope_files 逐一对照,未触碰范围外文件
- [ ] [M] 幂等与副作用: 重复执行同一命令比对结果一致性;grep `rm -rf`/`git reset --hard` 等不可逆副作用
- [ ] [A] 可恢复性判定: 判定写操作是否有展示后执行/可恢复路径,不可逆副作用是否可控
  **可选思路**：
  1. 思路 A：dry-run 核验——以 dry-run/预演确认副作用范围（适用场景：命令支持 dry-run）
  2. 思路 B：影响面评估——评估不可逆操作的爆炸半径与恢复手段（适用场景：无 dry-run、直接执行）
- [ ] [M] 复杂度与分层: 统计新增逻辑嵌套深度,超 3 层登记;grep 跨层直连（UI 直连数据层等）
- [ ] [A] 结构合规判定: 判定超标是否已合理提取子函数、跨层直连是否属架构违规
  **可选思路**：
  1. 思路 A：圈复杂度工具——跑工具量化复杂度再判定（适用场景：有静态分析工具时）
  2. 思路 B：分层契约核对——对照架构分层契约判定直连是否违规（适用场景：有明确分层约定时）
- [ ] [M] 常量与配置: 行为参数集中在配置/常量区,同义魔数 grep 无 3 处以上散落

## 证据要求
- 呼应 Rule 43.1 证据先行:每个「已完成/正确/通过」的重要声称必须附机器可复现证据（命令+关键输出 / Read 路径+关键行 / diff 行号,三选一以上）。
- 未验证内容显式登记「未验证」,禁止混入完成表述;CHANGES_REQUESTED 的证据指向具体 file:line,建议修法可直接执行。
- 返回模板 evidence 字段的结论行必须可用同一命令重跑复现,抽查即对证据原文。
- 证据与结论同会话落盘 checkpoint/findings,保证跨会话可复查。
- 证据路径统一写 `file:line` 或「命令+关键输出」两种形式,与兜底池其他成员对齐。

## 输出合约
- 结论二值: `APPROVED`（清单全过且 P0/P1 = 0）或 `CHANGES_REQUESTED`（任一 P0/P1 命中）,结论置于审查报告首行供机械解析。
- **审查对象总清单（Rule 70①）**：报告须附本次审查对象文件清单（绝对路径+逐项一句话），使收报告者无需追问即知审了什么。
- CHANGES_REQUESTED 必须附逐条问题清单,格式每行一条: `[P0|P1|P2] <file:line> — 问题 — 建议修法`。
- 级别定义: P0=阻断（正确性错误/不可回滚/测试回归）; P1=合并前必须修复; P2=建议不阻断。
- APPROVED 必须附各维度实际跑过的证据关键输出摘要;「无证据应该没问题」不受理。
- 审查完成后清除本次 checkpoint 中的临时中间产物,只保留结论与证据索引。
