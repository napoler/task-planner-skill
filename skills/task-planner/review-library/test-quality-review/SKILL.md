# test-quality-review · 测试质量审查

review-library 兜底池的测试领域审核技能,消费 Rule 42.2 四级检测链第④层。当任务产出为测试用例/测试套件/夹具/断言逻辑的新建或修改（含对既有测试的修复）时,用本技能按测试质量维度做专项审查——审的是「测试本身的质量」,不是被测代码。
输出二值 `APPROVED` / `CHANGES_REQUESTED`,每条结论必须附机器可复现证据。

## 触发条件
- Rule 42.2 四级检测命中第④层「task-planner 内置 review-library 兜底池」,且任务类型为测试/测试套件变更 → 命中本技能。
- 任务产出含 ≥1 个测试文件（test_*/*_test.*/spec/tc 脚本等）的新建或修改,或被测代码变更需同步评审配套测试。
- 交付前做「测试质量门」,或用户/审查者显式要求「测试质量」审查。
- 测试改动伴随实现改动时,与 code-quality-review 分工:本技能只管测试面,实现面归 code-quality-review,不重复审查。
- 纯文档、纯配置、无测试产出的任务不触发。
- 修复 flaky 测试、稳定化既有测试套件的任务同样命中本技能（修的是测试面本身）。

## 审查清单
每维度可直接执行（明确检查动作+判定标准）,禁空洞套话:
- [ ] [M] 断言有效性: Read 每条新断言,grep 恒真模式（`assertTrue(true)`/自比较/永真条件）确认 0 命中;枚举关键路径（正常/失败/回滚分支）的断言覆盖清单
- [ ] [A] 断言充分性判定: 判定每条断言是否真实验证了行为（vs 仅形式覆盖）、关键路径覆盖是否充分,不止「不抛异常即过」
  **可选思路**：
  1. 思路 A：变异测试——人为改坏实现，看断言是否失败（适用场景：断言数量多、怀疑形式覆盖时）
  2. 思路 B：路径-断言映射——逐关键路径核对是否有对应断言且断言落在真实行为上（适用场景：路径清晰、断言可枚举时）
- [ ] [M] 边界与异常用例: 枚举每个被测函数的边界例（空/极值/越界）与异常例（非法输入/依赖失败）覆盖清单,缺则登记缺口
- [ ] [A] 缺口必要性判定: 判定缺口是否属「必须覆盖」的关键边界（vs 不可达/无意义边界）
  **可选思路**：
  1. 思路 A：等价类划分——按输入域等价类确定必测边界（适用场景：输入域明确、参数化测试）
  2. 思路 B：故障注入——模拟依赖失败/非法输入，检验是否被覆盖（适用场景：外部依赖多、异常路径复杂时）
- [ ] [M] 隔离性: grep 测试间共享可变全局（模块级变量/fixture 未重置/写真实磁盘后不清理）;每个测试可单独跑通,顺序无关
- [ ] [M] 确定性: 无 flaky 源——grep `sleep`/随机数/时间戳/网络真实调用;确需随机则固定 seed,确需时序则注入时钟,mock 外部依赖
- [ ] [M] 夹具与数据管理: grep 用例体内内联测试数据与 fixture 目录使用情况;核对 setup/teardown 成对,检测跨用例残留脏数据
- [ ] [A] 数据组织判定: 判定数据散落是否影响可维护性、残留脏数据是否构成隔离缺陷
  **可选思路**：
  1. 思路 A：集中 fixture——测试数据统一收归 fixture 目录/工厂（适用场景：多用例共享数据、数据量大）
  2. 思路 B：用例内联——数据强绑定单用例时保留内联并注释说明（适用场景：数据仅本用例使用、语义自包含）
- [ ] [M] 覆盖缺口: 对照变更 diff 的函数/分支清单,逐条标注「有测试/无测试」并登记原因
- [ ] [A] 豁免判定: 判定无测试面是否可豁免（如纯声明/trivial 改动）,并评估风险;禁止静默跳过
  **可选思路**：
  1. 思路 A：风险分级——按改动影响面给无测试项定级，高风险必补测（适用场景：改动跨模块、影响面大）
  2. 思路 B：豁免清单——建立可豁免类型清单（getter/常量等），清单外一律补测（适用场景：改动量大、需快速分档）
- [ ] [M] 命名与可读性: grep 测试名逐条核对是否含「被测对象+场景+期望」;统计单用例断言簇数,超 5 则登记待拆分
- [ ] [A] 命名达意判定: 判定命名是否达意（vs 机械符合模板）、超标用例应如何拆分
  **可选思路**：
  1. 思路 A：陌生人视角——仅凭测试名推断被测量与期望，推断不出即命名不合格（适用场景：公共测试/他人维护）
  2. 思路 B：断言聚类拆分——按断言簇语义聚类拆为多用例（适用场景：单用例断言过多、职责混杂）
- [ ] [A] mock 合理性: 每个 mock 确认只桩化外部边界（网络/文件系统/时间/随机）,不 mock 被测对象自身逻辑;断言落在真实行为上而非 mock 回声
  **可选思路**：
  1. 思路 A：边界分类法——按外部边界（网络/文件系统/时间/随机）逐一分类核验 mock 范围（适用场景：mock 数量多、边界类型多时）
  2. 思路 B：断言溯源——追踪每条断言的取值来源，判断是否仅回显 mock 设定值（适用场景：断言脆弱或可疑时）
- [ ] [M] 失败可诊断性: 本地跑 1 例故意失败,记录断言失败信息原文
- [ ] [A] 可诊断性判定: 判定失败信息是否含期望值/实际值/定位线索（非裸 `assert False`）,是否需读源码才能归因
  **可选思路**：
  1. 思路 A：直接可读性测试——仅凭失败输出能否定位问题（适用场景：断言库支持自定义消息时）
  2. 思路 B：归因成本评估——评估需读多少源码才能归因，成本高即判不合格（适用场景：无消息定制能力、裸断言时）
- [ ] [M] 回归防护: 对历史 commit 试跑新增测试或做逻辑核对,记录在旧代码上的通过/失败结果
- [ ] [A] 回归性质判定: 判定该测试是否确为回归防护（旧代码必失败）而非快照复读
  **可选思路**：
  1. 思路 A：旧码试跑——checkout 修复前 commit 跑新测试，失败即确认为回归测试（适用场景：git 历史可回溯）
  2. 思路 B：逻辑核对——分析测试断言是否直接命中 bug 根因（适用场景：无法试跑旧码、需快速判断）
- [ ] [M] 越界自检: 变更文件清单与任务书 scope_files 逐一对照,未触碰范围外文件
- [ ] [M] 套件健康: 跑全量测试套件记录基线（通过/失败数）,比对新增用例 0 回归
- [ ] [A] 失败归因判定: 判定失败用例归因（本次改动 vs 历史债务）并登记,不混入本次改动
  **可选思路**：
  1. 思路 A：基线对照——与改动前基线逐一对照，差异项归因（适用场景：有稳定基线记录时）
  2. 思路 B：逐例溯源——对每个失败用例查 git blame/复现路径判定归属（适用场景：基线缺失、失败项多）
- [ ] [M] 覆盖度量: 有覆盖率工具则跑工具确认新增代码行覆盖不降;无工具则对照 diff 函数清单逐条人工登记「已测/未测+原因」
- [ ] [M] 断言独立性: 随机构造单用例失败,检测后续用例是否受污染;核对失败堆栈定位到用例行
- [ ] [A] 污染归因判定: 判定污染源（共享全局状态/fixture 未重置）并归因
  **可选思路**：
  1. 思路 A：乱序执行——打乱用例顺序跑，暴露顺序依赖（适用场景：怀疑用例间隐式依赖时）
  2. 思路 B：单例隔离跑——逐个用例单独执行，比对与套件跑的差异（适用场景：隔离性缺陷定位）

## 证据要求
- 呼应 Rule 43.1 证据先行:每个「已完成/正确/通过」的重要声称必须附机器可复现证据（命令+关键输出 / Read 路径+关键行 / diff 行号,三选一以上）。
- 未验证内容显式登记「未验证」,禁止混入完成表述;CHANGES_REQUESTED 的证据指向具体 file:line,建议修法可直接执行。
- 返回模板 evidence 字段的结论行必须可用同一命令重跑复现,抽查即对证据原文。
- 证据与结论同会话落盘 checkpoint/findings,保证跨会话可复查。
- 证据路径统一写 `file:line` 或「命令+关键输出」两种形式,与兜底池其他成员对齐。

## 输出合约
- 结论二值: `APPROVED`（清单全过且 P0/P1 = 0）或 `CHANGES_REQUESTED`（任一 P0/P1 命中）,结论置于审查报告首行供机械解析。
- **审查对象总清单（Rule 70①）**：报告须附本次审查对象文件清单（绝对路径+逐项一句话），使收报告者无需追问即知审了什么。
- CHANGES_REQUESTED 必须附逐条问题清单,格式每行一条: `[P0|P1|P2] <file:line> — 问题 — 建议修法`。
- 级别定义: P0=阻断（恒真断言/flaky 污染/回归防护失效）; P1=合并前必须修复; P2=建议不阻断。
- APPROVED 必须附各维度实际跑过的证据关键输出摘要;「无证据应该没问题」不受理。
- 审查完成后清除本次 checkpoint 中的临时中间产物,只保留结论与证据索引。
