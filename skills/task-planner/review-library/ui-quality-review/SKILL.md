# ui-quality-review · UI/前端质量审查

review-library 兜底池的前端领域审核技能,消费 Rule 42.2 四级检测链第④层。当任务产出为页面、组件、交互流程等 UI/前端代码或界面变更,且需要质量把关时,用本技能按 UI 质量维度做专项审查。
输出二值 `APPROVED` / `CHANGES_REQUESTED`,每条结论必须附机器可复现证据。

## 触发条件
- Rule 42.2 四级检测命中第④层「task-planner 内置 review-library 兜底池」,且任务类型匹配为「UI/前端页面/组件/交互流程交付」→ 命中本技能。
- 任务产出含前端源码（组件/模板/样式）或界面截图产物,且界面质量影响交付结论。
- 交付前做「UI 质量门」,或用户/审查者显式要求「界面/交互/前端质量」审查。
- 命中专用审查规则的任务优先专用规则;本技能只处理兜底池内 UI 面,不替代、不叠加。
- 纯后端/纯数据任务不触发;仅改动 API 契约而不动界面的,归 code 面审查。
- 审查需附界面证据（浏览器实测截图/渲染预览）,无运行环境时须显式登记「仅静态审查+未实测」并下调置信度。
- 多端交付（桌面+移动）时响应式断点面按 P1 对待而非 P2,逐断点各取 1 屏抽查。

## 机械 SOP（77.2 锚点）
固定可复用的 UI 审查机械步骤,先跑完本段再进入逐维度清单,保证机械步骤可复现、可校验:

1. [M] 断点截图：对 375px / 768px / 1440px 三个断点各生成 1 张全页截图
2. [M] 布局检查：`grep -n "overflow\|hidden\|absolute" <component>` 识别布局风险点
3. [M] 可访问性检查：`grep -n "aria-\|role=\|alt=" <component>` 检查语义标签
4. [M] 文案一致性：`grep -o "placeholder\|label\|title" <component> | sort | uniq -c` 检查文案复用
5. [M] 性能基线：`lighthouse <url> --format=json` 或 `curl -o /dev/null -w '%{time_total}' <url>` 记录加载时间
6. [M] 输出二值结论：PASS/FAIL + 逐行 `[P0|P1|P2] <file:line> — 问题 — 建议修法`

## 审查清单
每维度可直接执行（明确检查动作+判定标准）,禁空洞套话:
- [ ] [M] 布局完整性: 在目标分辨率下截图各区域;长文案与极端数据（空/超长/特殊字符）各取 1 样本实测并留截图
- [ ] [A] 布局缺陷判定: 目视判定有无错位/溢出/截断/重叠
  **可选思路**：
  1. 思路 A：全区域扫视——按栅格逐区目视检查（适用场景：区域少、布局规整）
  2. 思路 B：极端样本冲击——以极端数据触发边界布局问题（适用场景：动态内容、数据长度不可控）
- [ ] [M] 响应式表现: 在声明的关键断点（移动/平板/桌面）各取 1 屏截图;检测横向滚动条是否意外出现
- [ ] [A] 断点崩坏判定: 判定断点间有无布局崩坏
  **可选思路**：
  1. 思路 A：断点逐个走查——按声明断点逐个截图比对（适用场景：断点少、明确）
  2. 思路 B：连续缩放扫描——连续缩放窗口观察崩坏临界点（适用场景：断点多、需查断点间区间）
- [ ] [M] 交互反馈: 抽查主按钮/表单 3 个交互点,逐态（hover/active/loading/错误态）触发并记录反馈存在性
- [ ] [A] 反馈可感知判定: 判定反馈是否可感知、有无点了无响应的死交互
  **可选思路**：
  1. 思路 A：逐态触发——逐个交互态手动触发观察反馈（适用场景：交互点少）
  2. 思路 B：事件监听核查——读代码核查事件绑定是否覆盖各态（适用场景：交互点多、手测成本高）
- [ ] [M] 可访问性: 键盘 Tab 走查主流程记录焦点顺序;计算正文对比度与 WCAG AA 最低要求比对;grep 交互控件语义标签/aria
- [ ] [A] 可达性判定: 判定有无焦点陷阱、读屏可识别性是否达标
  **可选思路**：
  1. 思路 A：读屏实测——用读屏工具走查主流程（适用场景：有无障碍工具/要求高）
  2. 思路 B：语义审计——静态审计 aria/语义标签覆盖（适用场景：无读屏工具、快速筛查）
- [ ] [M] 文案一致性: grep 同类操作（保存/提交/取消）的按钮与提示语全文措辞统一,无同义词混用、无中英夹杂失控
- [ ] [M] 加载性能感知: 记录首屏加载时长与主路径等待时长;grep 骨架屏/懒加载/进度提示实现
- [ ] [A] 等待体验判定: 判定是否存在白屏长尾、有无超过 5s 的死等
  **可选思路**：
  1. 思路 A：网络限速实测——限速下走查主路径观察等待体验（适用场景：需模拟弱网）
  2. 思路 B：性能面板分析——用浏览器性能面板定位长任务与阻塞点（适用场景：有 DevTools、需量化定位）
- [ ] [M] 空态与异常态设计: 构造空数据/加载失败/无权限 3 态并截图
- [ ] [A] 兜底设计判定: 判定 3 态是否有显式空态文案与重试/兜底出口（vs 裸白屏/报错堆栈）
  **可选思路**：
  1. 思路 A：状态注入实测——通过 mock/接口拦截注入 3 态（适用场景：可控制数据源）
  2. 思路 B：代码路径走查——读异常分支代码核对兜底出口（适用场景：无法注入状态时）
- [ ] [M] 浏览器兼容面: 按声明的兼容矩阵在各目标浏览器打开并截图;未声明矩阵时登记「兼容面未定」
- [ ] [A] 静默失效判定: 判定某浏览器下有无样式/功能静默失效
  **可选思路**：
  1. 思路 A：矩阵逐浏览器走查——逐浏览器打开关键页比对（适用场景：兼容矩阵明确、浏览器少）
  2. 思路 B：特性检测预判——按 API/CSS 特性支持表预判风险点再验证（适用场景：浏览器多、优先排查高风险特性）
- [ ] [A] 视觉规范一致性: 抽查 3 个页面/组件,间距/字号/色板与设计规范（design token/样式变量）对照,无游离魔法值
  **可选思路**：
  1. 思路 A：token 反查——grep 游离值并与 design token/样式变量逐一对照（适用场景：有 token 体系/样式变量时）
  2. 思路 B：页面并排目视——抽 3 个页面/组件并排比对间距/字号/色板（适用场景：无 token、凭视觉规范判断时）
- [ ] [M] 关键路径可用性实测: 走一遍核心用户路径（如注册→首用）并留截图/日志证据
- [ ] [A] 可用性判定: 判定路径是否可完成、有无阻断报错
  **可选思路**：
  1. 思路 A：端到端实走——完整走一遍主路径（适用场景：路径清晰、环境可用）
  2. 思路 B：分支覆盖走查——在主路径外补走关键分支（适用场景：存在条件分支、需覆盖异常流）
- [ ] [M] 越界自检: 变更文件清单与任务书 scope_files 逐一对照,未触碰范围外文件

## 证据要求
- 呼应 Rule 43.1 证据先行:每个「已完成/正确/通过」的重要声称必须附机器可复现证据（命令+关键输出 / Read 路径+关键行 / diff 行号,三选一以上）。
- UI 审查的证据=实测界面产物（截图/渲染预览/浏览器日志）+逐项清单结论,禁未实测即下结论;「界面应该没问题」不受理。
- 未实测维度显式登记「未实测+原因」,禁止混入通过表述;CHANGES_REQUESTED 的证据指向具体 file:line 或截图文件名,建议修法可直接执行。
- 返回模板 evidence 字段的结论行必须可重跑复现（同一命令/同一页面重开即可复核）;证据与结论同会话落盘 checkpoint/findings,保证跨会话可复查。
- 证据路径统一写 `file:line` 或「命令+关键输出」两种形式,与兜底池其他成员对齐。

## 输出合约
- 结论二值: `APPROVED`（清单全过且 P0/P1 = 0）或 `CHANGES_REQUESTED`（任一 P0/P1 命中）,结论置于审查报告首行供机械解析。
- CHANGES_REQUESTED 必须附逐条问题清单,格式每行一条: `[P0|P1|P2] <file:line|截图名> — 问题 — 建议修法`。
- 修法须指认到组件/文件级（文件+行号或组件名）,可直接交给前端开发执行。
- 级别定义: P0=阻断（主路径不可用/布局崩坏/安全可见缺陷）; P1=合并前必须修复; P2=建议不阻断。
- APPROVED 必须附各维度实测证据关键输出摘要;「无证据应该没问题」不受理。
- 审查完成后清除本次 checkpoint 中的临时中间产物,只保留结论与证据索引。
- 截图证据须与审查时页面状态一致（同构建/同数据样本）,防后续改动使结论失效。
