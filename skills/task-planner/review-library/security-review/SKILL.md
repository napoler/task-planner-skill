# security-review · 安全审查

review-library 兜底池的安全领域审核技能,消费 Rule 42.2 四级检测链第④层。当任务产出引入新的外部输入面、凭据处理、权限变更、文件/网络操作,或用户/审查者显式要求安全审查时,用本技能做专项安全审查。
输出二值 `APPROVED` / `CHANGES_REQUESTED`,每条结论必须附机器可复现证据。

## 触发条件
- Rule 42.2 四级检测命中第④层「task-planner 内置 review-library 兜底池」,且任务类型为安全相关变更 → 命中本技能。
- 任务产出含外部输入拼接进 SQL/命令/路径/模板,或新增/修改凭据、密钥、token 的读取与存储路径。
- 任务变更权限模型（ACL/角色/最小授权）,或新增文件操作（读/写/删/下载）与网络出站。
- 交付前做「安全门」,或用户/审查者显式要求「安全」审查。
- 纯文档、无外部输入面与凭据路径的纯内部逻辑改动不触发（由 code-quality-review 兜底）。
- 系统接入新第三方 API/webhook、新增出站数据流的变更,入站与出站载荷均过本清单。

## 审查清单
每维度可直接执行（明确检查动作+判定标准）,禁空洞套话:
- [ ] [M] 注入面: grep 所有 SQL/命令/路径/模板拼接点,列出用户可控输入参与拼接的位置
- [ ] [A] 注入风险判定: 判定每处是否已参数化/白名单/转义,字符串拼接外部输入入 shell/SQL 定级 P0
  **可选思路**：
  1. 思路 A：污点追踪——从外部输入源追踪到 sink 判定是否被净化（适用场景：数据流复杂、拼接点多）
  2. 思路 B：拼接点逐一审查——逐处人工判定参数化/转义情况（适用场景：拼接点少、可枚举）
- [ ] [M] 密钥与凭据: grep 仓内新增文本的硬编码密钥/token/密码/私钥（常见前缀 `sk_`/`AKIA`/`ghp_` 等）;确认为硬编码 = P0,须改环境/密钥管理注入
- [ ] [M] 输入验证与转义: 枚举每个外部输入入口（参数/文件/网络载荷）的类型与长度校验;grep 输出到 HTML/日志/命令处的转义调用
- [ ] [A] 验证充分性判定: 判定校验与转义是否充分覆盖 XSS 与日志注入面
  **可选思路**：
  1. 思路 A：入口-出口配对——为每个入口配对校验，每个出口配对转义（适用场景：入口出口可枚举）
  2. 思路 B：payload 注入——以 XSS/日志注入 payload 实测（适用场景：有运行环境、可实测）
- [ ] [A] 权限与最小授权: 新代码所需权限核对最小必要集;确认无默认 root/sudo 提权路径、无未鉴权即可触达的写操作
  **可选思路**：
  1. 思路 A：权限清单 diff——列出新代码所需权限与最小必要集逐项 diff（适用场景：有权限声明/清单可对照时）
  2. 思路 B：攻击面走查——从「未鉴权可达」视角走查写操作与提权路径（适用场景：Web/服务端接口类变更）
- [ ] [M] 敏感数据日志: grep 日志/错误路径中打印密码/token/PII 的点;确认脱敏或改打占位符,无全量敏感值入日志
- [ ] [M] 依赖漏洞面: 新增/升级依赖跑已知漏洞检查（CVE/audit 工具）;无高危未修复依赖引入,版本固定可追溯
- [ ] [M] 不安全反序列化: grep `pickle.loads`/`yaml.load`（无 SafeLoader）/`eval`/`JSON.parse` 直接吃外部数据;确认外部来源数据只走安全解析器
- [ ] [M] 文件操作路径穿越: grep 所有以外部输入参与的路径 join/打开操作,列出缺少 canonicalize + 前缀校验的位置
- [ ] [A] 越根可达判定: 判定越根路径可达性并定级 P0（目标须在声明根目录内）
  **可选思路**：
  1. 思路 A：穿越 payload 实测——以 `../` 类 payload 实测越根可达性（适用场景：有运行环境）
  2. 思路 B：静态路径分析——静态分析 join 结果是否可能逃逸根目录（适用场景：无法实跑、路径构造复杂）
- [ ] [M] 网络通信加密: 出站 URL 一律 https（grep `http://` 新增点）;无内网明文传输凭据,证书校验未关闭（禁 `verify=False`/`-k` 默认开）
- [ ] [M] 审计留痕: grep 写操作/权限变更/删除操作的审计日志调用;grep 危险命令（`rm -rf`/`git reset --hard`/`curl|bash`）自动执行路径
- [ ] [A] 留痕完备判定: 判定审计日志是否含操作者+时间+对象三要素、危险命令是否授权可控
  **可选思路**：
  1. 思路 A：日志字段核验——逐审计点核对三要素完整性（适用场景：审计点少、结构化日志）
  2. 思路 B：操作回放——模拟操作看是否留下可追溯痕迹（适用场景：日志非结构化、需实证）
- [ ] [M] 越界自检: 变更文件清单与任务书 scope_files 逐一对照,未触碰范围外文件
- [ ] [M] 配置暴露面: 新增配置文件不在仓内泄漏环境敏感值（.env 类文件不入仓）;接口无未鉴权的调试端点遗留
- [ ] [M] 错误信息泄露: grep 异常回传前端/日志处的堆栈/内部路径/版本指纹输出
- [ ] [A] 泄露判定: 判定是否存在信息泄露、错误文案是否统一脱敏
  **可选思路**：
  1. 思路 A：异常触发实测——触发异常观察回传内容（适用场景：有运行环境）
  2. 思路 B：错误处理路径审计——静态审计异常处理分支的输出内容（适用场景：无法触发、分支多）
- [ ] [M] 会话与鉴权面: grep 新增鉴权 token/cookie 设置处,列出 HttpOnly/Secure/来源校验属性配置
- [ ] [A] 安全属性判定: 判定安全属性是否完备、有无会话固定面
  **可选思路**：
  1. 思路 A：属性逐项核对——对照 HttpOnly/Secure/SameSite 清单逐项核验（适用场景：cookie 设置点集中）
  2. 思路 B：会话生命周期走查——走查登录-续期-登出全周期找固定面（适用场景：会话逻辑复杂）

## 证据要求
- 呼应 Rule 43.1 证据先行:每个「已完成/正确/通过」的重要声称必须附机器可复现证据（命令+关键输出 / Read 路径+关键行 / diff 行号,三选一以上）。
- 未验证内容显式登记「未验证」,禁止混入完成表述;CHANGES_REQUESTED 的证据指向具体 file:line,建议修法可直接执行。
- 返回模板 evidence 字段的结论行必须可用同一命令重跑复现,抽查即对证据原文。
- 证据与结论同会话落盘 checkpoint/findings,保证跨会话可复查。
- 证据路径统一写 `file:line` 或「命令+关键输出」两种形式,与兜底池其他成员对齐。

## 输出合约
- 结论二值: `APPROVED`（清单全过且 P0/P1 = 0）或 `CHANGES_REQUESTED`（任一 P0/P1 命中）,结论置于审查报告首行供机械解析。
- CHANGES_REQUESTED 必须附逐条问题清单,格式每行一条: `[P0|P1|P2] <file:line> — 问题 — 建议修法`。
- 级别定义（本技能特化）: P0=阻断（注入/密钥泄漏类问题一律 P0,以及不可回滚的权限放大）; P1=合并前必须修复; P2=建议不阻断。
- APPROVED 必须附各维度实际跑过的证据关键输出摘要;「无证据应该没问题」不受理。
- 审查完成后清除本次 checkpoint 中的临时中间产物,只保留结论与证据索引。
