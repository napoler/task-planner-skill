# Context Corrector

定位句：否定/矛盾触发→上下文与历史文档整理纠正；整理先于继续（Rule 98.3）：触发后先清污染面再推进任务，禁止带着已知缺陷继续执行。

## 触发判据

### T1 用户显式面（Rule 98.1）
1. 否定方案/结论（措辞如「错了」「不对」「缺陷」「还是不行」）。
2. 同一问题反馈≥2次（意味着相关上下文或记录存在缺陷）。
3. 指出记录文档错误（如要求「整理上下文」「纠正记录」「文档矛盾」「结论不一致」「历史文档有错」「context corrector」）。

### T2 自主面（Rule 98.2）
1. 新证据推翻已落盘结论。
2. 两条记录互斥（前后文矛盾，无法同时为真）。
3. 执行结果证伪先前假设。

命中任一即调用本技能。

## SOP 六步

### Step 1: 基线锚定 [M]
- 逐字引用触发源原话（T1 或 T2 场景），并以 `file:line` 落锚到触发证据（用户消息、diff、测试输出、日志等）。
- 将触发源原话与锚点写入 `progress/findings`，防止整理过程自身漂移。
- 明确「整理范围」假设，如存在多种理解需标注「未验证」而非擅自选定（衔接宪法 §四 / Karpathy §13.1）。

### Step 2: 污染面枚举 [M]
逐项勾选穷举以下载体表，识别受污染结论及其引用点：

| 载体 | 检查要点 |
|------|----------|
| 会话上下文 | 当前会话中已接受并用于决策的结论、假设、待办表述 |
| 计划文档 `plans/*` | 计划目标/验收/步骤中引用的错误结论或过时假设 |
| 记忆文件 | 持久化记忆中与新证据冲突的条目 |
| 进度账本 `.zcode/ledger/` | 账本条目中已记录的结论、状态表述 |
| 注册表 `INDEX` | 注册表索引项中引用的错误结论或路径表述 |
| 用户所指历史文档 | 用户明确指出或 Step 1 锚定的历史文档 |

**append-only 豁免清单（Rule 98.4）：** `user-session-log.md` 与 `.zcode/ledger/` 账本只允许**追加**「更正 #N：原结论 X 作废，因 Y（引用 Step 1 触发源）」条目。**禁改写、禁删除**既有行。其余载体按 Step 3 处置规则处理。

### Step 3: 处置三分 [M]
按以下优先级处理每项污染结论（拿不准时降级，且优先选可逆方案）：

| 方式 | 适用 | 要求 |
|------|------|------|
| ① 修正当地 | 结论明确错误且能就地替换且无历史追溯依赖阻碍 | 就地改动，**注明修改原因/时间/原行为**（Rule 45 双层注释）。改动前后均需可追溯。 |
| ② 标 `superseded` | 需保留历史溯源、上下游仍可能引用、或暂不宜强行改写 | 保留原文，在原文附近加「`superseded by <新结论>（日期+原因）`」，保留 `file:line` 溯源。**默认优先于 ③**，可逆性最高。 |
| ③ 授权删除 | 仅当确系孤立且无引用价值、且删除符合宪法 §五 写入最小化与孤儿代码双规则 | **先展示将删内容（diff/片段）→ 等待用户确认 → 执行**。对属于 append-only 豁免清单的条目**一律不适用** ③，改用追加更正条目。 |

**原则：** 默认 ① > ② > ③；如拿不准或影响范围存疑，**降级到 ②（可逆优先）**。

### Step 4: 修正条目即时落盘 [M]
- 每个处置当刻写入持久层，**禁攒批**。
- 写入内容须包含：修正值、更正原因、**Step 1 触发源引用**（原话 + `file:line`）。
- 涉及 append-only 载体时，仅按 Step 2 豁免清单方式追加，不触及既有行。
- 修正需与宪法 §五「展示后执行」（非征询停摆）配合，但命中需用户确认的场景（如 Step 3 ③）仍遵守确认要求。

### Step 5: 下游阻断 [M]
- 整理未完成前，将已识别的被污染结论标记「**禁用引用**」。
- 后续步骤、派发 prompt（子代理 prompt）中**删引用、改更正值**，避免将污染结论传递给下游。
- 若发现已在进行中的步骤强依赖被污染结论，**暂停该步骤**直至完成处置或获得用户决策。
- **未阻断即继续 = 污染扩散**，视为整理不合格。

### Step 6: 复验清零 [M]
- 使用 `grep` 检查旧结论关键词：命中数应为 **0**，或全部命中均带 `superseded` 标记。
- `Read` 抽查已改载体 **≥1 处**，复核处置方式与 Step 3 是否一致。
- 在 `progress` 记「**整理收口**」行，需包含：**污染面 N 项 + 处置 ①/②/③ 计数 + 复验结果**（附 grep 命令输出或 `file:line` 抽查证据）。
- 复验未通过→返回 Step 2，直至清零或产出可验证的阻断报告并等待用户决策。

## 非目标声明

- **零新增机器守卫：** 本技能为纯文本 SOP 条款档，遵循宪法 §四.6 opt-in 原则。**未获用户授权**，不新增脚本/hook/自测断言/registry 机器门。
- **不改写既有条款原文：** 只在触发点按需引用既有规则（Rule 31/32/65/80 等），**既有条款段原文零改动**。如需指针仅以引用方式添加，不做结构性重写。
- **规则全文在 task-discipline 纪律域 Rule 98：** 本文件为**执行 SOP 载体**。参照 Rule 82 分层先例（同 `error-fix-prompt-forge`、`todo-skill`），纪律域规则权威在 `task-discipline`，执行细节落在本技能文件。

## 产出形态

整理完成时，按以下四行输出（简洁、可观察）：

1. **触发源（T1/T2+原文）：** `T1|T2` + 逐字触发源原话 + `file:line` 锚点
2. **污染面清单（N 项）：** 列出受影响载体（会话上下文/`plans/*`/记忆文件/`.zcode/ledger/`/`INDEX`/用户所指历史文档）及关键污染结论
3. **处置计数（①/②/③）：** ①修正当地 / ②标 superseded / ③授权删除 各自计数
4. **复验结果（清零证据 file:line 或命令输出）：** `grep` 旧结论关键词结果（0 或全带 `superseded`）、`Read` 抽查 `≥1` 处的 `file:line`，及 `progress`「整理收口」行摘要
